# 工具与技能门控配置指导

这份指导给"按用户要求配置工具可见性"的场景用：用户想按技能解锁工具、想彻底屏蔽某个工具，或门控结果和预期不一致时，照下面的步骤做。

## 门控怎么工作

- **直接可用**：绑定文档里没有的工具，插件完全不碰。
- **技能解锁**：文档里列出的工具默认对所有 Agent 隐藏；某个会话成功加载了绑定它的技能后，这些工具才出现在该会话里。
- **始终拦截**：`blockedTools` 里的工具永远隐藏，任何技能都解锁不了。一个工具同时出现在两处时，以拦截为准。
- 可见性按 Agent 分别判定，并且只在会话内有效；恢复会话时会从会话日志重建已加载的技能，所以解锁状态能挺过恢复。

## 唯一持久状态：绑定文档

- 路径由宿主决定：设置页最下方「绑定文件」显示本次实际生效的绝对路径，以它为准，不要凭记忆写死。
  - 进程由 `dsh` 以某个 profile 启动时（桌面端、`dsh web` 都属于这种情况），生效文件归该 profile 所有：`<profile 目录>/skill-gate/bindings.json`，默认形如 `$DSH_HOME/profiles/<profile>/skill-gate/bindings.json`。这个 profile 文件存在与否都不影响旧全局文件：旧的 `$DSH_HOME/skill-gate/bindings.json` 不会被自动读取或改写，只在 profile 文件还没建立、而旧文件存在时，由设置页给出「导入旧规则」按钮，用户点了才复制一次。
  - 只有进程没有 profile 身份时，生效文件就是旧的全局文件 `$DSH_HOME/skill-gate/bindings.json` 本身，直接读写它即可；这种情况下没有"导入"这回事。`$DSH_HOME` 默认 `~/.dsh`，Windows 上是 `C:\Users\<用户>\.dsh`。
  - 插件配置里显式写了 `bindingPath` 时以配置为准；profile 内和共享位置都能用配置覆盖。
  - 同一 `$DSH_HOME` 下不同 profile 各存一份，互不影响；不要把某个 profile 的规则直接抄到另一个。
- 格式（`version` 必须是 `1`）：

```json
{
  "version": 1,
  "bindings": [
    { "skill": "ssh", "tools": ["ssh_exec", "ssh_upload"] }
  ],
  "blockedTools": ["browser_click"]
}
```

- 一个技能一行；同名技能的多行会合并；`tools` 与 `blockedTools` 都必须是非空字符串数组。
- 文件写坏会让门控**整体失效**（工具全部直接可见，插件只打告警），所以每次写完都要回读校验。
- 改绑定不需要重启 DSH：Agent 创建时读一次，之后每次技能加载再读。只有改插件代码才需要重新构建并重启。

## 引用暂时缺失的名字

- 技能或工具现在不存在，不影响写规则：门控不会因为查不到名字就丢弃或改写这一行。照着写就行，等它真正注册后规则自动恢复生效，不需要再动文档。
- 设置页会把这些名字标出来——工具行显示「当前未注册」，技能列表里对应的技能旁显示「未找到的技能/未解析」，页面顶部给一条警告，列出当前目录里没有的技能名。**这是提示，不是报错**，保存按钮照常可用。
- 目录读不出来（插件或技能系统没就绪）时标记为「未解析」，同样不阻塞。这种情况下不要仅凭目录为空就删规则。
- 常见来源：工具属于还没开始的那类插件、技能是用户自定义或即将安装的、或者名字写错了。写错了直接改名字；确实还没装就保留规则并告诉用户。
- 反过来，用户要"彻底移除某个工具"而该工具不存在时：把它写进 `blockedTools` 照样有效，以后它出现了也会被拦。

## 推荐流程

1. 先读绑定文档，看清现有的 `bindings` 与 `blockedTools`。
2. 核对名字：技能名要用本会话技能目录里真实存在的名字；工具名要是真实注册的工具名。设置页「技能门控工具」展示的是全量并集（包括还没开始的会话里的工具），拿不准就请用户在页面上确认。模型侧看不到被隐藏的工具，所以"我的工具表里没有"不能当证据。
3. 做最小改动：只动请求涉及的那个工具，以及需要维护的技能行（见下一节）。不要顺手整理、删除或重排其它行——请求只涉及一个技能或一个工具时，其余内容原样保留。
4. 把整份文档写回同一个文件，保持 `version: 1` 和未涉及的字段不变。
5. 回读同一文件，逐项核对最终内容，把改动前后的差异报给用户。
6. 提醒用户重新打开会话（或新开会话）最可靠：已经打开的会话不会因为改绑定而追溯隐藏已经解锁的工具。

## 三种规则怎么选，怎么改到位

工具随时都该能用 → 不要登记；工具该按需出现 → 在 `bindings` 里绑定到能代表它的技能；工具根本不该出现 → 放进 `blockedTools`。已经登记过的工具改换规则时，**先清旧的、再落新的**，否则旧登记会继续生效：

- 改成**直接可用**：从每个 `bindings[i].tools` 里删掉该工具，同时从 `blockedTools` 里删掉它。两处都清干净后，工具才真正回到不登记状态。
- 改成**技能解锁**：从 `blockedTools` 里删掉该工具（拦截优先，留着就永远不会解锁），再把它加进本次选定的技能行；该技能还没有行就新建一行。工具若仍在别的技能行里，保留——一个工具可以被多个技能解锁。
- 改成**始终拦截**：把它加进 `blockedTools`，并从每个 `bindings[i].tools` 里删掉它；其它技能行里就不该再看到它。

只改目标工具；同一行里的其它工具、其它技能行原样保留。

## 让 Agent 知道该加载哪个技能

建议同步优化负责解锁工具的技能描述（`SKILL.md` 的 `description` 或插件注册的描述）：写清适用场景、代表性的工具名，并提示使用这些工具前先加载该技能。工具尚未解锁时，Agent 仍可根据技能目录中的描述找到入口。

例如，`meme` 技能的描述可以写成：「用于查找和发送表情包；需要使用 `send_meme` 等表情工具时，先加载本技能以解锁工具。」

这是对已安装技能的加载提示。修改其他技能的描述前，先确认用户授权与该技能的维护方式；插件提供的技能应从其注册来源更新。

## 排查

- 工具没出现在会话里：确认它确实在 `bindings` 里、技能名拼写正确、并且本会话已经成功加载过该技能。
- 加载技能后还是不出现：工具可能同时在 `blockedTools` 里（拦截优先）。
- 所有工具都出现了：绑定文档多半无效（JSON 语法或字段类型），按插件告警修复文件。
- 只在某个子代理里出现或不出现：可见性按 Agent 独立，子代理要各自加载技能。
- 需要机器可读快照时，设置页读的是 `GET /skill-gate`（以及 `GET|PUT /skill-gate/bindings`），它受连接信任栅栏保护，Agent 侧直连通常返回 401/403；这种情况下直接读写绑定文档。

## 完成证据

- 绑定文档的最终原文。
- 改了哪一行、为什么。
- 用户重新打开会话后应该看到什么（包括仍被标记为未注册/未找到的名字）。
